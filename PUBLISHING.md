# Release checklist

This source-built Home Assistant app is kept in version control for development. An initial source push is not a stable release, license selection, security certification or completion of the checks below. Keep experimental status until the remaining release gates are complete.

## Owner decisions

- [x] Repository owner/name: `raegen/ha-forge`; initial development branch: `main`. The remote had no branches before initial preparation.
- [x] The owner approved the Git author identity and enabled the repository's SSH connection for read/write. Private keys and passwords are not stored in this repository.
- [x] Set the actual repository URL and maintainer in `repository.yaml`, and the app URL in `forge/config.yaml`.
- [ ] Choose a license and add its full approved text as `LICENSE`. No license was selected on the owner's behalf; licensing remains an unresolved release decision.
- [ ] Configure a private vulnerability-reporting route and document it in `SECURITY.md`.

## Technical release gate

- [ ] Review the repository and any existing commit history: no options, credentials, personal context, conversations, attachments, backups, diagnostics, maintenance scripts or generated test reports. Filename/header checks are not a complete secret scanner.
- [ ] Run the Python suite, JavaScript checks and CI from a fresh checkout.
- [ ] Build the aarch64 image through Home Assistant Supervisor or an isolated builder. Source-only checks do not prove the container builds.
- [ ] Verify real HA Ingress, live model discovery and a harmless read-only provider task after activation. Follow [the testing guide](forge/TESTING.md).
- [ ] Verify explicit account SSH-key creation, independent host pinning, read access and an authorized commit/push to a disposable remote repository. A read test does not prove provider write access. See [SSH setup](forge/SSH.md).
- [ ] Verify key identity and retained data across a same-identity Supervisor update/restore. No production key is generated by packaging; tests that recreate an in-process manager are not container-persistence proof.
- [ ] Verify fresh installation and an existing local in-place update separately. Never test by deleting the user's data.
- [ ] Inspect permissions and map mounts. Forge is an admin development tool with Supervisor manager access, not a general household assistant.
- [ ] Keep `stage: experimental` until attended validation is complete. Do not call this a security audit or a production certification.
- [ ] Review/pin CI action revisions and base-image policy for the public repository's maintenance policy.
- [ ] With explicit publication permission, initialize/review/stage/commit this source-only repository and push the chosen branch. Forge 0.6 supports this through structured Git tools without unrestricted shell. Do not force-push over existing history.
- [ ] Publish release notes and, if desired, create tag `v0.6.0` using the provider's release UI. Forge's structured tools do not create or push tags. Packaging does not automatically push, tag or upload anything.

## Layout and installation identity

Home Assistant reads `repository.yaml` at repository root and `forge/config.yaml` in the app directory. No prebuilt image is declared; Supervisor builds from the Dockerfile. The generic base image is explicitly supplied by `FROM` rather than relying on an implicit `BUILD_FROM` value.

Public slug: `forge`. Legacy local slug: `smartass_forge` (intentionally preserved only on the existing appliance). Moving between repository/local identities does not migrate private app data. Plan and authorize that separately, stop the old worker before starting a migrated one, and preserve consistent backups.
