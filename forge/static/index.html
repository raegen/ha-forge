Development permissions

Only you can change this setting. Push also needs provider-side write access, your publication request, and an active Allow changes task. Existing read-only connections stay read-only until you change them.

Persistence, backups & access boundaries

Keys live in the app’s private /data/ssh, not the container image. Normal updates of this same installation are designed to retain them. Backups contain credentials: protect and encrypt backups. A separately installed repository app has a different identity and does not automatically inherit keys or history.

Forge can initialize projects under addons/ or share/, review diffs, stage selected files, commit, switch branches, fetch, fast-forward and push a single reviewed branch. It can also shallow-clone into a new share/forge_git/ directory. No force push, destructive reset, automatic merge, remote shell, private-key export or OAuth. No repository code runs automatically.

Account scope is intentionally broad: the Git provider decides which repositories the account key can access. Choose a per-repository key for narrower provider-side access. Forge’s read-only switch limits its Git tools; it does not reduce a key’s provider permissions or constrain unrestricted shell access.

Disabling prevents future use but keeps the key and cannot retract in-flight work. Remove its public key at the provider to revoke remote access. To rotate, explicitly create and test a replacement, then disable and revoke the old connection. Nothing is automatically deleted or rotated.

Administrator or unrestricted shell access to this container can read its files, including private keys. This is not a separate credential vault. Keep shell disabled unless you accept that trust boundary.
